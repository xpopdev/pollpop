### CRITICAL

#### RT-BUG-01 — Mock `.pollpop-mock.json` write is corruptible under concurrency (Critical)

- **Repro:** 2 `POST /api/polls` in parallel (or 50 burst votes where each `persistMock()` does a full read-modify-write). `store.ts:getMock()` hydrates once, `persistMock()` does `fs.writeFileSync(file, JSON.stringify({polls,votes,events}, null, 2))` with no lock, no atomic rename, no queue. Parallel handlers interleave → last writer wins and the other poll/vote is lost; partial write on crash leaves invalid JSON and next boot wipes the DB (catch swallows and re-seeds).
- **Evidence:** `app/lib/store.ts:48-59` `persistMock()` + `22-46` `getMock()`; `70-71` seed re-applied only on first load. Gitignore lists `app/.pollpop-mock.json` but file is the de-facto dev DB.
- **Fix:** Do not rely on file DB for correctness; treat it as best-effort cache. Replace with `writeFileSync(tmp) → rename(tmp, file)` (atomic on POSIX) and add try/catch that never throws. Better: gate `persistMock` behind a single-flight queue (`p-limit(1)`). Add startup check: if JSON parse fails, keep empty DB and log to server console rather than silently re-seeding and losing all history.

#### RT-BUG-02 — Supabase fallback read-then-write still loses votes when RPC migration not applied (Critical)

- **Repro:** Deploy prod without running `002_vote_rpc.sql`. Fire 50 concurrent `POST /api/polls/:id/vote` with distinct voters (group-chat spike). Each handler does `select votes` then `update votes = votes+1` — concurrent reads see the same base, one increment is lost per collision. The repo's own comment admits this race. Tests pass in mock (in-memory, single-process) but prod under load will undercount.
- **Evidence:** `app/lib/store.ts:285-339` — `atomicIncrement` tries `rpc("increment_vote")` then falls back to `select`+`update` (`329-330`) which races; `atomicDecrement` same (`335-337`). Migration `app/supabase/migrations/002_vote_rpc.sql` exists but is not auto-applied; `001_init.sql` does not create the functions. `DEPLOY.md`/Vercel deploy has no `supabase db push` step.
- **Fix:** (P0) Make deploy fail if RPCs missing: add startup check `select proname from pg_proc where proname in ('increment_vote','decrement_vote')` and return 500 with actionable message if absent. In parallel, change fallback to a single `update poll_options set votes = votes + 1 where id = ...` statement (atomic even without RPC) on Postgres — do not read then write. The current fallback must not ship.

#### RT-BUG-03 — Poll creation is not atomic — poll row can orphan if option insert fails (Critical)

- **Repro:** `POST /api/polls` with 4 options where one `image_url` is a 6 MB data URL that exceeds Postgres row limit / network timeout after the `polls` insert succeeded. `store.ts` inserts `polls` first, then `poll_options`. If `poll_options` insert throws, the poll remains with no options → `getPoll` returns poll with `options=[]`, UI shows "Whi? 0 options · 0 votes" and vote always 400.
- **Evidence:** `app/lib/store.ts:180-189` — two separate `insert`s with no transaction / rollback; error from `oErr` is returned as 500 but the `polls` row is not deleted. `app/app/api/polls/[id]/route.ts:7` serves empty options as valid.
- **Fix:** Wrap in a Postgres transaction or use a single RPC `create_poll_with_options`. At minimum, on `oErr` delete the just-created poll row and surface a retryable error. Add DB check `exists (select 1 from poll_options where poll_id = polls.id)` or UI guard for 0-option polls.

### HIGH

#### RT-BUG-04 — Mock vs Supabase dedup semantics diverge — last-wins breaks differently in prod (High)

- **Repro:** Voter clears cookie (or uses incognito) but keeps IP. Mock finds `existingByCookie` (cookie-only) and treats as change-vote (`store.ts:236-242`); Supabase queries `voter_cookie AND ip_hash` (`320`) so same user with cleared cookie creates a second vote row → total increments by 1 instead of shifting. Conversely, voter keeps cookie but changes IP (mobile network hop) → mock finds by cookie alone, prod misses and double-counts.
- **Evidence:** `app/lib/store.ts:232-243` (mock) vs `318-345` (Supabase). Variables `key`/`voteKey` computed but discarded (`281`). Comment on line 224-225 claims dedup by cookie if present but Supabase branch ignores that.
- **Fix:** Unify policy: dedup key = `hash(voter_cookie)` if present, else `ip_hash`, with `unique (poll_id, voter_cookie)` where `voter_cookie` is null-able and `ip_hash` fallback via coalesce. Or document last-wins as cookie-only and downgrade ip_hash to rate-limit only. Add a cross-branch integration test asserting mock≡prod dedup.

#### RT-BUG-05 — OG route serves SVG on edge — broken on WhatsApp / Discord / Telegram unfurl (High)

- **Repro:** Share `/p/{id}` on WhatsApp. Crawler fetches `/api/polls/{id}/og`. Response is `image/svg+xml` (`app/app/api/polls/[id]/og/route.ts:81-87` `x-pollpop-og: svg-edge`). WhatsApp/Discord/iMessage strip SVG → link shows no preview. The route's own header comment (lines 10-25) documents this as TODO(P0-4) but it shipped as the only implementation. `next.config.js` sets `dangerouslyAllowSVG: true` which does not fix external crawlers.
- **Evidence:** `app/app/api/polls/[id]/og/route.ts:4` `runtime="edge"` + `81-87` SVG response; `4-34` sharp failing on edge is not the issue — the fallback is the only path and it is SVG. `app/app/p/[id]/page.tsx:12` advertises og:image as `/api/polls/{id}/og` so every share is affected. `sharp` is in `package.json:21` but never imported.
- **Fix:** Per file's own TODO, switch OG to `runtime="nodejs"` + `sharp` or `vercel/og` PNG. Keep SVG only as fallback when PNG import throws. PNG must be `image/png` with `cache-control: public, max-age=3600`. Pre-render PNG at create time to Supabase Storage `poll-images` bucket as alternative.

#### RT-BUG-06 — Metrics CTR / K-factor are gameable and denominator is unstable (High)

- **Repro (CTR):** Open `/p/{id}` in 10 tabs → `PollClient` fires `poll_view` once per mount per tab but dedup is only `sessionStorage` per tab (`PollClient.tsx:46-51`), so 10 views counted. Scroll to CTA in one tab → `cta_view` fires once, click once → `CTR = 1/10 = 10%` passes binding threshold (0.08) with trivial inflation. Reloading without clearing session doubles again. Event endpoint has no dedup, no auth, no rate limit.
- **Repro (K-factor):** `POST /api/events` with `ref=poll_xxx` and `poll_create_complete` counts as viral attribution (`store.ts:383,438` `ref.startsWith("poll_")`). Anyone can `curl /api/events` with arbitrary ref to inflate `via_cta` and K-factor. `ref` on poll create is taken from request body without verifying it matches an existing poll.
- **Evidence:** `app/lib/store.ts:376-395,426-448` metric math; `app/app/api/events/route.ts:12-23` no validation of `poll_id` existence; `app/components/CTACard.tsx:15-16` `poll_view`/`cta_view` guards are client-only; `app/app/metrics/page.tsx:29` labels ESTIMATE but `verdictLabel` still drives PASS/KILL copy.
- **Fix:** Server-side dedup: `unique (cookie, name, poll_id, date_trunc('hour', created_at))` at least for `poll_view`/`cta_view`, or HLL. Validate `ref` exists in `polls` before counting toward K. Gate `derived` on minimum sample (`poll_view ≥ 50`) before showing verdict; otherwise show "insufficient data". Rate-limit `/api/events` (e.g. 60/min/IP).

#### RT-BUG-07 — Create API truncates before validating — label>24 never rejected via HTTP (High)

- **Repro:** `POST /api/polls` with `label:"X".repeat(100)` → `app/app/api/polls/route.ts:16` `String(obj.label).slice(0,24)` silently chops to 24, then `store.ts:132` sees 24-char label and passes. The intended 400 (`Each label 1–24 chars`) is unreachable through the API. Direct `createPoll()` call would 400, but the only prod entry is the API.
- **Evidence:** `app/app/api/polls/route.ts:13-19` vs `app/lib/store.ts:131-132`. Test `lib/store.test.ts:90-100` expects 400 for 25-char label but exercises `store` directly, not the route (so it passes while route would not).
- **Fix:** Remove `slice(0,24)` in the route; pass raw label to `createPoll` and let it validate. Return field-level errors so UI can show "label ≤24".

#### RT-BUG-08 — No rate limit on Supabase poll creation (High)

- **Repro:** `store.ts` rate-limits `createPoll` only in mock branch (`140-148` `5 creates / IP / hour`). Supabase branch (`175-192`) has no `rate` check — `void hashIpSync` is computed but not used. Attacker scripts `POST /api/polls` → unbounded poll spam, storage blowup, SEO poisoning.
- **Evidence:** `app/lib/store.ts:175-179` Supabase create path — no `rate` map, no `votes.count` check, no 429. Compare mock path `142-148`.
- **Fix:** Add server-side rate limit for create (e.g. 5/hour/IP + 20/day/cookie) backed by `events` or a dedicated `rate_limits` table. Return 429 with `retry-after`.

#### RT-BUG-09 — Vote rate limit counts only inserts, not lookups — bypass via cookie rotation (High)

- **Repro (bypass):** Supabase vote rate counts `votes` rows with `ip_hash` in last 24h (`318`). If voter clears cookie between votes, each is a new IP+cookie combo? Actually with cookie cleared, insert succeeds as new row → counts toward rate. But mock `store.ts:230-239` only increments `rate` for `isNew` votes and skips on change-vote; Supabase does same (`322`). So attacker who alternates option (change-vote) avoids ever hitting 10? No — change doesn't insert, so rate array not grown, so 100 change-votes are free. Rate limit is for new polls, but change-vote bypasses it (intended). The bug is attacker can create new polls with 10 IPs then vote 10 each → 100 votes from one actor via IP rotation (no IP allowlist). More directly: mock `rcKey` is `vote:{poll}:{ip_hash}` but Supabase counts by `ip_hash` only — mismatch again.
- **Evidence:** `app/lib/store.ts:229-239,317-322` two rate implementations diverging.
- **Fix:** Unify as token bucket per IP+cookie in DB with `pg_advisory_lock` or middleware. Cap at 10 per poll per 24h regardless of insert vs change (changes shouldn't reset rate).

#### RT-BUG-10 — Failure recovery leaks internal errors to clients (High)

- **Repro:** Send malformed JSON to `POST /api/polls` → `catch (e)` returns `NextResponse.json({ error: e.message }, { status: 500 })` where `e.message` may contain stack, env hints, or Supabase `pErr.message` with table/column names. Same on `/vote` (`route.ts:36-38`) and `/events` (`route.ts:25-27`). No `500` envelope hides internals.
- **Evidence:** `app/app/api/polls/route.ts:41-43`, `app/app/api/polls/[id]/vote/route.ts:36-38`, `app/app/api/events/route.ts:25-27`. `supabase` errors include Postgres detail when RLS or schema mismatched.
- **Fix:** Map known errors (400/429) through; for 500 return generic `"Something went wrong — retry"` and log detail server-side. Ensure OG never throws (it already has double fallback, good).

### MEDIUM

#### RT-BUG-11 — Profanity filter word-boundary fix is real but scope is title-only (Medium)

- **Repro:** Create poll with `context: "fuck this fit"` or `label: "xxx hot"` — passes. `badRe` tested only against `title` (`store.ts:138`), not `context` or `label`. UI hints that images are user-supplied; NSFW image content has zero detection (no Cloud Vision / NSFW model) — only filename gate in `CreateForm`.
- **Evidence:** `app/lib/store.ts:136-138` five regexes, only `re.test(title)`; migration allows any `context text`/`label text`. `components/CreateForm.tsx:28` checks `f.type`/`f.size` only.
- **Fix:** Apply same word-boundary check to `context` + `label` and add server-side image check (at least file-type + size in `route.ts`). Tier-2: add Supabase Storage + Cloud Vision / `nsfwjs` async flag with `status='flagged'`.

#### RT-BUG-12 — XSS via label / title injection into SVG is escaped but not hardened (Medium)

- **Repro:** Title `"><script>alert(1)</script>` — `og/route.ts:39-40` does `escapeXml` which replaces `& < > "` but not `'`, so SVG is safe today. However `PollClient.tsx:158-163` renders `poll.title`/`poll.context`/`poll.id` as text nodes (safe), but `label` is rendered into `<b>{o.label}</b>` without sanitization. React escapes HTML, so low severity for now. The risk is SVG served without `Content-Security-Policy` header; SVG can contain JS if attacker bypasses escape (e.g. `onload` inside injected tag if escape is bypassed).
- **Evidence:** `app/app/api/polls/[id]/og/route.ts:27-29` `escapeXml`; `app/app/p/[id]/PollClient.tsx:152-164` text interpolation.
- **Fix:** Keep React escaping but also sanitize `title`/`label` on write (strip `< > &` or HTML-encode). Add `Content-Security-Policy: default-src 'none'` + `X-Content-Type-Options: nosniff` on OG response. Escape `'` as `&#39;` in SVG.

#### RT-BUG-13 — Sticky CTA overlaps content and is not dismissible (Medium)

- **Repro:** At 375px viewport, scroll to bottom of `/p/{id}` after voting. `globals.css:172-174` makes `.cta-card` `position: sticky; bottom: 12px` on `max-width:640px`. CTA sits over `ShareRow` and last result bars; no close affordance, no `z-index` isolation against `toast` (`z:60`). Keyboard open pushes it offscreen on iOS.
- **Evidence:** `app/app/globals.css:172-174` sticky CTA; `app/components/CTACard.tsx:42-53` full-height card; `app/app/p/[id]/PollClient.tsx:189` renders CTA last.
- **Fix:** Limit sticky to `compact` variant only or add `max-height: 40dvh` + dismiss `×` that sets `sessionStorage.pollpop_cta_dismissed`. Ensure `padding-bottom: 88px` on `.poll-wrap` already exists (`90px` line 99) — verify it clears sticky height on 375px.

#### RT-BUG-14 — Mobile vote grid at 375px collapses to 1 column — 4-option poll requires excessive scroll (Medium)

- **Repro:** Poll with 4 options at 375px. `globals.css:113-118` forces `.vote-grid.cols-4` to `1fr 1fr` above 380px, `1fr` only below 380px. At exactly 375-380px it's `1fr` (single column) → 4 images stacked, vote CTA is below fold, first paint shows only 1 option. `cols-3` also becomes `1fr` at 380px which is arguably correct for 3 but not for 4 where 2×2 is expected.
- **Evidence:** `app/app/globals.css:113-119`, `app/components/VoteGrid.tsx:15` col logic.
- **Fix:** Keep `cols-4` as `1fr 1fr` down to 340px (2×2 grid), only collapse to `1fr` under 340. Add explicit breakpoint testing (Plan: add Playwright 375px viewport test).

#### RT-BUG-15 — Optimistic vote can go negative then reconcile with stale server counts (Medium)

- **Repro:** Poll starts 0-0. User A and B vote simultaneously for different options. Client optimistically does `o.votes +1` (`PollClient.tsx:98-107`). Server returns `counts` that reflect only one of the votes (the other racily lost or not yet committed). UI briefly shows 1-0 then snaps to 1-0 anyway, but if the user's own increment was lost via fallback race (RT-BUG-02), poll shows 0-0 after "Vote counted ✓" toast — misleading. No retry on mismatch.
- **Evidence:** `app/app/p/[id]/PollClient.tsx:98-125` optimistic delta vs server `counts` reconciliation; `interval 5000` fallback may paper over this but not fast enough to prevent misperception. `votedRef` prevents double-fire locally (`88,135`) but not across tabs.
- **Fix:** Don't toast "Vote counted" until server `200`. On `counts` mismatch where client's choice has 0, re-fetch once and show "Retrying…" rather than success.

#### RT-BUG-16 — PollClient Realtime subscription leaks and filter may never fire (Medium)

- **Repro:** Component mounts, subscribes to `client.channel(`poll:${id}`).on("postgres_changes", { table:"poll_options", filter:`poll_id=eq.${id}` })`. Supabase Realtime requires the table be in `supabase_realtime` publication (`001_init.sql:81-85` comments say "Run manually"). If not added, subscription connects but never fires → silent fallback to 5s polling, which is not surfaced to user. Unsubscribe uses `channel as {unsubscribe}` (`81`) but `supabase-js` v2 uses `supabase.removeChannel(channel)` — unsubscribe may no-op and leak channels on re-render.
- **Evidence:** `app/app/p/[id]/PollClient.tsx:63-85` subscription vs `app/lib/supabase.ts`; `001_init.sql:81-85` publication commented out.
- **Fix:** In Supabase dashboard, run `alter publication supabase_realtime add table poll_options;`. In code, call `supa.removeChannel(ch as RealtimeChannel)` and handle `subscribe` status callback to log when Realtime is unavailable (show "Live updates via polling" hint).

#### RT-BUG-17 — Cookie handling trusts `x-pollpop-cid` header over httpOnly intent (Medium)

- **Repro:** `POST /api/polls` and `/vote` accept `x-pollpop-cid` header as authoritative dedup key (`route.ts:24-25`, `vote/route.ts:15-16`). This header is JS-writable and attacker-controlled; cookie is not `httpOnly` (`dedup.ts:27` `SameSite=Lax` only). Attacker can set any `x-pollpop-cid` per request → effectively choose dedup key, bypassing rate limits that are keyed by it.
- **Evidence:** `app/app/api/polls/route.ts:24-25`, `app/app/api/polls/[id]/vote/route.ts:15-16`, `app/lib/dedup.ts:26-27`.
- **Fix:** Prefer `cookie` header as canonical; treat `x-pollpop-cid` as fallback only when cookie missing, and on first use set `Set-Cookie` with `HttpOnly; Secure; SameSite=Lax` via server (requires middleware). Document that vote identity is soft, not hard.

#### RT-BUG-18 — Image uploads are data URLs persisted as poll_options.image_url — unbounded size (Medium)

- **Repro:** `CreateForm.tsx:32-37` reads file via `FileReader → dataUrl` and sends that as `image_url` in `POST /api/polls`. A 5 MB JPEG → ~6.6 MB base64 data URL. 4 options → ~26 MB JSON body per poll, stored as `poll_options.image_url text` (unbounded `text` column). Next.js body limit (~1-4 MB default) will 413, but if bypassed, DB bloats and `/p/{id}` page ships 26 MB of base64 to every voter.
- **Evidence:** `app/components/CreateForm.tsx:25-37`, `app/app/api/polls/route.ts:13-21` no body size check, `001_init.sql:23` `image_url text not null` unbounded.
- **Fix:** Use Supabase Storage `poll-images` bucket (commented in `001_init.sql:38-39` but never enabled). Upload via `/api/upload` (missing — no such route; task lists it but file doesn't exist). Enforce server max 5 MB per image, 20 MB per poll, and rewrite data URLs to `https://.../poll-images/...` before insert. Add `image_url check (octet_length(image_url) < 2048)` or similar to reject data URLs in DB.

#### RT-BUG-19 — Events `meta` is unbounded JSON — DoS vector (Medium)

- **Repro:** `POST /api/events` with `meta: { data: "x".repeat(1_000_000) }` → `recordEvent` inserts raw `meta` as `jsonb` with no size check (`store.ts:367-368` Supabase path `insert(row)`). Attacker can bloat `events` table. `ref` is sliced to 120 (`events/route.ts:18`) but `meta` is not.
- **Evidence:** `app/app/api/events/route.ts:19` `meta && typeof meta === "object"` without size/truncation; `001_init.sql:56` `meta jsonb` unbounded.
- **Fix:** Cap `meta` to 2 KB serialized, strip keys > 64 chars, drop values > 512 chars. Return 413 if oversized.
