# RLS Tightening — 2026-08-14 (RT-SEC-01)

**Finding:** `app/supabase/migrations/001_init.sql:74-87` created `allow all` policies (`using (true) with check (true)`) on `polls`, `poll_options`, `votes`, `events` with RLS enabled. Anyone holding the `NEXT_PUBLIC_SUPABASE_ANON_KEY` (shipped to every browser via `lib/supabase.ts:supaAnon()`) could `POST`/`PATCH`/`DELETE` any row via the PostgREST endpoint `https://<project>.supabase.co/rest/v1/...`, bypassing all `lib/store.ts` validation (title length, 2-4 options, dedup, rate limits).

**Fix — migration `app/supabase/migrations/003_rls_tighten.sql`:**

- Drops the four permissive policies (`allow all polls` / `allow all options` / `allow all votes` / `allow all events`).
- Replaces each with two idempotent policies (`drop policy if exists` + `create`):
  - `anon read <table>` — `for select using (true)` on `polls`, `poll_options`, `votes`, `events`. Anon (browser) can still read — matches current client usage (`PollClient.tsx`, `metrics`, `supaAnon()` reads).
  - `service write <table>` — `for all using (auth.role() = 'service_role') with check (auth.role() = 'service_role')` on all four tables. Only the `service_role` key can insert/update/delete.
- Idempotent and re-runnable (`drop policy if exists` guards both old and new names; handles the `allow all options` vs `allow all poll_options` naming drift).

**Why this matches actual usage:** all writes already go through Next.js API routes (`app/app/api/polls/route.ts`, `app/app/api/polls/[id]/vote/route.ts`, `app/app/api/events/route.ts`) → `lib/store.ts` (`createPoll`, `voteOnPoll`, `recordEvent`) → `supaService()` / `supaAdmin()` (`lib/supabase.ts:19`, `lib/supabase-admin.ts`) which uses `SUPABASE_SERVICE_ROLE_KEY` (server-only, never `NEXT_PUBLIC_`). Direct Supabase writes from the browser were never intended — `supaAnon()` is now read-only by policy and any direct PostgREST `INSERT`/`UPDATE`/`DELETE` with the anon key returns 0 rows / RLS denial.

**What must not change:**

- API routes **must** continue to use `supaService()`/`supaAdmin()` for every write (and for vote-count RPCs `increment_vote`/`decrement_vote` from `002_vote_rpc.sql`). Switching an API route to `supaAnon()` will silently fail to write (RLS denies `auth.role()='anon'`).
- `SUPABASE_SERVICE_ROLE_KEY` must stay server-only (never `NEXT_PUBLIC_`, never imported from a client component — already enforced by `supabase-admin.ts` boundary; see `red-team-2026-08-14.md:RT-SEC-15`).
- Keep RLS enabled on all four tables (set in `001_init.sql:69-72`; `003` does not disable it).

**Deploy steps:**

1. `supabase db push` or `psql $DATABASE_URL -f app/supabase/migrations/003_rls_tighten.sql` (apply after `001`/`002`).
2. Verify: with only the anon key, `select` succeeds but `insert into polls ...` is denied; with `service_role` key both succeed. Quick check: `curl -H "apikey: $ANON_KEY" -H "Authorization: Bearer $ANON_KEY" https://<project>.supabase.co/rest/v1/polls -d '{"id":"t","title":"x"}'` should no longer create a row.
3. If the project was ever public with the permissive policies, rotate the anon key in Supabase dashboard after deploying.
4. If a future feature needs browser-direct writes (e.g. beacon without API hop), add a narrow `for insert with check (...)` allowlisting `name`/`poll_id exists`/size — do not re-add `allow all`.
